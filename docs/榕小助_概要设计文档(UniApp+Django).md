# 榕小助 APP 概要设计文档

## 1. 系统总体架构

系统采用经典的前后端分离 C/S 架构，兼顾移动端的高效适配与后端复杂AI逻辑的处理。
- **前端表现层 (UniApp)**：采用 Vue3 语法，基于 UniApp 框架开发。一次开发即可编译为 Android/iOS APP，且便于后期拓展至微信小程序或H5页面，满足移动办公的敏捷需求。
- **后端服务层 (Django)**：采用 Python Django 框架结合 Django REST Framework (DRF) 构建 RESTful API。Python 在对接 LLM（大语言模型）、音频处理、向量数据库等方面具有天然的生态优势。
- **数据与AI支撑层**：关系型数据存储使用 MySQL/PostgreSQL，缓存与异步任务队列依赖 Redis；知识库检索引入向量数据库（如 Milvus 或 Chroma），AI能力通过调用外部大模型 API（或私有化部署的 LLM）及语音识别（ASR）API实现。

## 2. 核心模块技术设计

### 2.1 知识库问答智能体模块
- **技术实现 (RAG架构)**：
  - **文档处理**：Django 后端通过定时任务，将业务人员上传的政策、资费文档进行分块（Chunking），调用 Embedding 模型转化为向量并存入向量数据库。
  - **智能问答**：APP端发起提问，后端接收后，在向量数据库中进行相似度检索，将匹配到的上下文知识与用户问题组装成 Prompt，调用 LLM 生成专业回答并流式（SSE）返回给 UniApp 端。
- **核心组件**：LangChain/LlamaIndex (Python)、Vector DB。

### 2.2 录音转文字与AI总结模块
- **数据采集**：UniApp 调取原生设备的麦克风与录音 API，生成音频文件（后续可扩展通过蓝牙接入智能工牌进行录音）。
- **异步处理链路**：
  1. 考虑到走访录音文件较大且处理耗时，音频通过分片上传至对象存储（OSS/MinIO）。
  2. Django 接收上传完成信号后，将任务推入 Celery 异步队列。
  3. Celery Worker 调用第三方 ASR 接口（如科大讯飞、阿里云等，可定制通信行业热词）进行语音转写。
  4. 转写完成后，通过预设的业务 Prompt 调用 LLM 进行语义总结，提取关键待办信息。
  5. 通过 WebSocket 将处理完成的通知及生成的待办清单推送到客户端。

### 2.3 智能待办与清单管理模块
- **LBS 地理围栏**：UniApp 持续获取后台定位权限，在客户端计算当前坐标与目标坐标的距离，触发“到达某地”的本地推送通知。
- **时间提醒机制**：基于 Celery Beat 或 APScheduler 在 Django 后端建立分布式定时任务，到期后通过极光推送等第三方通道下发 APP 消息。
- **语音创建任务**：短语音指令通过轻量级 ASR 接口实时转义，提取时间、地点、事件等要素（NER命名实体识别）自动填入待办表单。

### 2.4 分级通知与审批流模块
- **权限与额度控制**：
  - 在 Django 中设计 RBAC（基于角色的访问控制）模型，映射网格长、7岗、8岗等角色。
  - 采用 Redis 实现通知发送频次与额度的计数器（Rate Limiting 机制）。
- **审批工作流**：针对超额度的通知，设计轻量级状态机（Status Machine），记录“草稿-待审批-已驳回-已发布”状态，并通过消息队列通知对应 8 岗人员审批。

### 2.5 版本管理与热更新模块
- **前端实现 (UniApp)**：
  - 启动时通过 `uni.getSystemInfoSync()` 获取当前应用版本号（`version`）和构建号（`versionCode`）。
  - 请求后端版本检查 API，根据后端返回的 `update_type` 决定更新策略。
  - **热更新 (WGT)**：利用 `uni.downloadFile` 和 `plus.runtime.install`，在后台静默下载或提示下载 `.wgt` 资源包并重启应用生效，无需跳转应用商店。
  - **整包更新 (APK/IPA)**：利用全局路由守卫或启动页拦截，强制弹出更新弹窗，阻止用户进行其他操作，提供下载链接跳转。
- **后端支持 (Django)**：
  - 设计版本管理模型，包含：平台（Android/iOS）、版本号、构建号、更新类型（0: 提示热更, 1: 强制热更, 2: 提示整包, 3: 强制整包）、下载包URL、更新日志。

## 3. 数据库核心模型设计 (Entity-Relationship)

1. **User (用户表)**：包含工号、姓名、角色ID、所属机构（网格/区县/市公司）。
2. **VisitRecord (走访记录表)**：包含走访对象、音频文件URL、原始转写文本、AI总结文本、走访时间、关联业务类型。
3. **TodoItem (待办事项表)**：包含事项内容、触发类型（时间/地点/手动）、触发阈值（经纬度/时间戳）、状态（未办/进行中/闭环）、关联走访记录ID。
4. **Notification (通知分发表)**：包含标题、内容、发送层级、发送人、状态、关联审批工单ID。
5. **QuotaRule (通知额度规则表)**：配置各层级/专项的月度推送配额。
6. **AppVersion (应用版本表)**：包含平台类型(OS)、版本号、资源包/安装包URL、是否强制更新标识、更新日志说明。

---

## 4. 后续扩展接口设计 (API Gateway)
- **PC端支持**：Django 提供的 RESTful API 可无缝支撑后续 PC 端 Vue/React 框架的接入，共用核心业务逻辑。
- **IoT 硬件接口**：预留蓝牙设备数据上报接口与设备注册鉴权接口，确保后期智能工牌的数据安全接入。

---

## 5. 部署与运维架构
- **容器化部署**：前后端及中间件均采用 Docker 容器化打包，使用 Kubernetes 或 Docker Swarm 进行集群编排。
- **网络拓扑**：后端服务部署于移动公司内网服务器，通过 Nginx 进行反向代理与负载均衡。前端 APP 通过移动内部安全网关或 VPN 访问接口，确保数据不外泄。
