# 榕小助 APP 最小可行性产品 (MVP) 规划文档

## 1. MVP 目标与定位

### 1.1 MVP 核心目标
最小可行性产品（MVP）阶段的核心目标是**以最低的开发成本，最快速度验证核心业务假设**。
在“榕小助”项目中，MVP 阶段主要验证以下两点：
1. **走访数据留痕的有效性**：一线人员是否能适应并高频使用“录音转文字+AI总结”功能，该功能是否能有效降低走访记录的时间成本。
2. **信息触达的效率提升**：AI 知识库与基础的分级通知是否能切实减少产品经理的答疑负担。

### 1.2 上线受众与周期
- **灰度受众**：选取 1-2 个标杆区县/网格的客户经理及商客经理进行首批灰度测试。
- **验证周期**：MVP 上线后运行 2-4 周，收集核心转化数据与真实反馈。

## 2. MVP 功能范围界定 (Scope)

为了保证 MVP 的敏捷交付，对 PRD 中的全量需求进行裁剪，区分“MVP 必做”与“后续迭代（Phase 2+）”功能。

### 2.1 走访智能记录与总结 (核心保留)
- **MVP 包含 (In-Scope)**：
  - APP 内基础录音功能及录音文件上传。
  - 调用第三方 ASR 接口实现语音转文字。
  - 调用 LLM 进行基础的走访纪要提炼，并自动提取文本格式的待办事项。
- **暂不包含 (Out-of-Scope)**：
  - 弱网离线缓存与断点续传（MVP阶段要求在有网环境下操作）。

### 2.2 智能待办与清单管理 (适度裁剪)
- **MVP 包含 (In-Scope)**：
  - 待办列表的展示与基础状态流转（未办、已办）。
  - AI 自动推入的待办事项展示，以及简单的手动录入待办功能。
- **暂不包含 (Out-of-Scope)**：
  - LBS 地理围栏提醒（到达某地提醒）。
  - 复杂的定时任务推送提醒。
  - 语音创建待办指令（NER 实体识别）。

### 2.3 知识库问答智能体 (适度裁剪)
- **MVP 包含 (In-Scope)**：
  - 基于已导入的静态文档（通过后台预先导入），提供单轮/多轮的文本问答功能。
- **暂不包含 (Out-of-Scope)**：
  - “问题上报-产品经理解答-知识库更新”的完整审批闭环（MVP 阶段由管理员定期手动更新语料）。

### 2.4 分级重要通知触达 (适度裁剪)
- **MVP 包含 (In-Scope)**：
  - 基础的通知下发功能（网格、区县、市级）。
  - 开屏强制展示机制（重要3秒、紧急10秒）。
- **暂不包含 (Out-of-Scope)**：
  - 复杂的发送额度管控规则与 8 岗矩阵审批流（MVP 阶段仅对少数核心管理人员开放白名单发送权限，从源头控制数量）。

### 2.5 系统基础与版本管理 (核心保留)
- **MVP 包含 (In-Scope)**：
  - 基础的账号密码/验证码登录或单点登录（SSO）。
  - 热更新 (WGT) 与整包强制更新 (APK/IPA) 能力（保障灰度测试期间快速修复 Bug 的底线要求）。
- **暂不包含 (Out-of-Scope)**：
  - PC 端管理应用开发。
  - 智能工牌（IoT）硬件对接。

## 3. MVP 核心用户故事 (User Stories)

1. **作为一名客户经理**，我希望在走访客户时能一键开启录音，走访结束后系统能自动生成纪要和下一步的待办任务，以便我无需手动整理笔记，避免遗漏客户需求。
2. **作为一名市公司产品经理**，我希望把最新的资费政策录入系统后，客户经理可以直接向 AI 提问获取答案，以便减少我每天在微信群里重复答疑的时间。
3. **作为一名网格长**，我希望发送紧急通知时，员工打开 APP 必须强制阅读 10 秒，以便确保重要指标或政策能 100% 触达一线。

## 4. MVP 数据验证指标 (KPIs)

MVP 上线后，需重点监控以下业务数据以决定下一步产品走向：
- **走访功能渗透率**：每日活跃用户中，使用“走访录音”功能的用户占比。
- **AI 总结采纳率**：AI 生成的走访纪要与待办，被用户原样保存的比例（未进行大量二次手动修改）。
- **知识库解决率**：知识库问答中，用户未点击“点踩”或“无帮助”的会话比例。
